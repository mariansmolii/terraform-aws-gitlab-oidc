# Contributing

Thanks for taking the time to contribute! This document describes the development workflow and conventions used in this repository.

## Prerequisites

- [Terraform](https://developer.hashicorp.com/terraform/install) >= 1.3
- [pre-commit](https://pre-commit.com/)
- [terraform-docs](https://terraform-docs.io/) — used by the pre-commit hook to generate the README tables
- [TFLint](https://github.com/terraform-linters/tflint)

## Getting started

1. Fork and clone the repository.
2. Install the git hooks:

   ```bash
   pre-commit install
   ```

   This installs both the `pre-commit` and `commit-msg` hooks: formatting, validation, linting, docs generation, and commit message checks.

3. Create a feature branch from `main`.

## Making changes

- Run all checks locally before pushing:

  ```bash
  pre-commit run --all-files
  ```

- Keep `examples/complete` and the `Usage` section of the README in sync with any change to the module interface.
- Do not edit the part of `README.md` between the `BEGIN_TF_DOCS` / `END_TF_DOCS` markers by hand — it is generated by terraform-docs.

## Commit messages

Commit messages must follow [Conventional Commits](https://www.conventionalcommits.org/) and are validated by the `commit-msg` hook. Allowed types and their effect on the automated release:

| Type | Effect |
| ---- | ------ |
| `feat` | minor release |
| `fix`, `refactor`, `revert` | patch release |
| `docs`, `chore`, `ci` | no release |

For breaking changes, append `!` to the type (e.g. `feat!: ...`) or add a `BREAKING CHANGE:` footer — this triggers a major release.

Releases are fully automated with [semantic-release](https://github.com/semantic-release/semantic-release): when a merge to `main` passes CI, the version, `CHANGELOG.md`, and GitHub release are created automatically. Do not bump versions or edit the changelog manually.

## Pull requests

- Open pull requests against the `main` branch.
- CI runs the pre-commit suite against both the minimum and the latest supported Terraform versions; pull requests must be green.
- Keep pull requests focused — one logical change per PR.
